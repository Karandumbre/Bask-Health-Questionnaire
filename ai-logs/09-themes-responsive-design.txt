Stage 9 — Themes and Responsive Design

ME — Initial prompt

The admin form builder and patient intake screens are working. Now I want to add themes and make the layouts consistent on desktop and mobile.

The assignment needs at least three predefined themes, a Shuffle option that creates a fresh theme, and light/dark mode. Admins should be able to choose and publish a theme, but patients should only be able to switch between light and dark mode.

We are using Tailwind CSS and shared UI components. How should we structure the theme configuration without hardcoding colors in each screen? I also want the contrast to be accessible.

AI Response —

Keep theme values separate from React components. Define semantic color tokens such as page background, surface, primary action, text, muted text, borders, focus, and error colors. Each preset should provide both light and dark values.

Start with three named presets: Ocean, Emerald, and Slate. Map their tokens to CSS variables scoped to the form preview and patient intake container. Shared components should read those variables instead of checking which preset is active.

The admin editor can have theme controls for:
- Choosing Ocean, Emerald, or Slate
- Switching the preview between light and dark
- Generating a new palette through Shuffle

Save the selected theme with the draft and copy its light/dark token values into the published version. The patient page then renders the theme from that published snapshot and only exposes the light/dark toggle.

For accessibility, calculate text-to-background contrast and reject or adjust generated combinations that do not meet WCAG AA. Normal-sized text should reach at least 4.5:1, while large text should reach at least 3:1. Also test visible focus indicators, errors, selected fields, and disabled controls.

ME — Follow-up

For Shuffle, I don't want it to keep showing the same three themes with slightly different colors. It should actually generate a new combination each time. Also, what happens when I publish a form and later change its theme? I don't want the old patient form link to change.

And do we need separate components for mobile and desktop? It feels like we've already created many component files for a small assessment.

AI Response —

Shuffle should generate new palette values rather than randomly choosing an existing preset. Generate a candidate hue or set of hues, derive related surfaces and foreground colors for light and dark modes, and run contrast checks before accepting it. Compare the result with the currently active palette so consecutive Shuffle actions do not return an effectively identical result.

Keep draft and published themes separate:
- The draft stores the current editable theme.
- Publishing copies the complete theme into an immutable published snapshot.
- A later theme change updates the draft only.
- Republishing creates a new version with its own theme and public link.

That preserves the appearance of earlier published versions and sessions.

You don't need duplicate mobile and desktop component trees. Use the same question controls and shared primitives with responsive layouts. The admin editor can use a desktop-oriented three-panel arrangement and adapt to narrower widths; the patient intake should be mobile-first with readable labels, touch-friendly controls, and a simple progress header.

Separate components when they have different responsibilities or state behavior, not just because their CSS differs at a breakpoint.

ME — Follow-up

One concern: if the theme uses CSS variables, could the admin theme affect the whole dashboard? Also I want the patient to have only the light/dark option, not the preset selector or Shuffle button.

AI Response —

Apply theme variables to a dedicated preview or intake wrapper rather than the document root. That keeps the admin dashboard's styling stable while the form preview changes themes.

Use separate controls for the two experiences. The admin-side ThemeControls component owns preset selection and Shuffle. The patient interface only receives the published theme tokens and changes the active mode between light and dark. Do not expose a theme-editing API to patient routes.

Persist the patient's display-mode preference only if needed for usability; it must not modify the published theme stored in PostgreSQL. Reuse the shared form field components, but give the patient page its own responsive layout and progress presentation.

ME — Final response

Okay. Let's keep the themes token-based and scoped to the form preview and intake screens. Use Ocean, Emerald, Slate, and a Shuffle generator with contrast validation. The draft stores the editable theme, while each published version keeps its own snapshot.

Keep the patient interface mobile-first. Patients should only switch between light and dark, and there is no need to duplicate all the UI components for different screen sizes.

AI Response —

Agreed. The implementation can be split into three focused areas:

1. Theme domain logic: presets, token types, Shuffle generation, and contrast validation.
2. Theme presentation: CSS-variable mapping and admin controls.
3. Patient presentation: responsive intake layout and a light/dark toggle using published tokens.

Test that presets and generated palettes meet contrast requirements, theme changes persist in drafts, and older published links continue to render their original theme after a newer version is published.

Implementation reference

The existing Bask Health project has theme logic under src/features/themes/, shared design tokens under src/design-system/, shared controls under src/components/ui/, and responsive patient views under src/features/patients/. Published versions store a theme snapshot separately from the editable draft.
