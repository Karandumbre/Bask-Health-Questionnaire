Bask Health — Stage 3: Backend APIs and Frontend Integration

ME — Initial prompt

We have decided to use Next.js 16, Supabase Auth, Drizzle and PostgreSQL for the Bask Health assessment. The database schema is in place.

Now I want to connect the frontend to the backend. We need admin APIs to create, list, open, rename, update and delete forms, plus an API to publish a version and view submitted responses. On the patient side we need to load a published form, start a session, save progress, resume using a recovery code and submit answers.

Can you suggest the API routes, request/response format, and a simple way to call them from React? I want to keep things maintainable, with validation and security on the server. Please don't add GraphQL or a separate backend service unless necessary.

AI Response —

We can use Next.js App Router Route Handlers for all HTTP endpoints. Keep route.ts files thin: parse the request, verify authentication or the patient session capability, call a domain service and return a consistent JSON response.

Suggested route groups:

Admin:

- GET /api/admin/forms — list forms in an authorized workspace.
- POST /api/admin/forms — create a form and initial draft.
- GET /api/admin/forms/[formId] — load the current draft.
- PATCH /api/admin/forms/[formId] — rename or save draft changes.
- DELETE /api/admin/forms/[formId] — delete an unpublished form or archive a published one, following your lifecycle rules.
- POST /api/admin/forms/[formId]/publish — validate and publish a snapshot.
- GET /api/admin/forms/[formId]/responses — list submissions for the form.

Authentication:

- POST /api/auth/login
- POST /api/auth/logout
- GET /api/auth/me

Patient:

- GET /api/patient/forms/[slug] — load the published form definition and theme.
- Session endpoints for starting a session, checking current progress, saving progress, recovering access and submitting.

Keep patient session operations separate from admin routes. The public form GET is anonymous, but saving and submitting require a valid session capability.

Place database operations in server services such as src/features/forms/server/ and src/features/patients/server/. Shared request contracts and form rules belong in domain modules. Use Zod to check incoming JSON and return predictable errors with HTTP status codes.

ME — Follow-up

For the frontend, should we call these APIs using fetch or Axios? And how should the UI handle validation errors, expired sessions, or a 409 when the draft revision has changed?

AI —

Either fetch or Axios works. Use the shared Axios client and feature endpoint helpers to keep errors and cancellation consistent. Follow each endpoint's response contract.

The wrapper should:

- Use same-origin API URLs so browser cookies are included appropriately.
- Parse successful responses and handle failures consistently.
- Preserve HTTP status and machine-readable error codes.
- Avoid exposing raw server exceptions in the UI.

Use a shared response shape such as:

Success:
{ "success": true, "data": { ... } }

Failure:
{ "success": false, "error": { "code": "REVISION_CONFLICT", "message": "Draft changed", "details": { ... } } }

Adapt the exact success payload to each route's existing contract; don't force a refactor just to make every endpoint identical.

In the admin builder, keep the editable draft in React state. The autosave layer can send PATCH requests after a short debounce with expectedRevision. A 409 means the client must not silently overwrite a newer server draft. Keep the local edits and show a conflict resolution path.

For ordinary validation failures, show a useful message near the affected field. For an expired or invalid patient capability, explain the available recovery or new-session action rather than repeatedly retrying it; recovery cannot revive a session that has itself expired. For server or network failures, keep unsaved changes visible and offer retry.

ME — Follow-up

The patient page is public. How can we save progress without making users create accounts? Also, I don't want someone to modify another patient's session just by guessing an ID or changing the request payload.

AI —

A patient account is not necessary for this assessment. Generate a random session capability and issue an HttpOnly cookie with Secure enabled in production. Cookies use per-slug names and Path=/; server-side session and published-version checks enforce isolation. Verify capabilities using HMAC digests. Recovery also stores encrypted replacement credentials; keep that payload server-side.

Each patient mutation should read the cookie on the server, verify the capability against the correct session and published version, and validate the submitted answers using the saved published snapshot. Never trust client-supplied question definitions, session ownership or visibility flags.

For cross-browser recovery, provide a session reference and separate high-entropy recovery code. Verify both on the server, rate-limit failed attempts and rotate credentials after successful redemption.

Save progress using a session revision so two browser tabs cannot silently overwrite each other. When a conditional question becomes hidden, remove its old answer on the server as well as in the UI.

Submission should run in a PostgreSQL transaction, lock the session, validate all visible required answers and insert into submissions with a UNIQUE(session_id) constraint. If the browser retries after a successful commit, return the existing submission instead of creating another one.

ME — Final decision

Okay. Let's keep the Route Handlers small and use the existing domain and server services. I want one common Axios client, clear loading/error states, and no direct database access from Client Components. We can build the admin screens first and then integrate the patient screens using the same validation rules.
